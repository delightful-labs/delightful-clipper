# Startup performance

Implemented on `perf/startup`, based on `d09477d` (the merge of the previously measured `e658075`; application files are identical). No dependency, catalog or durable schema changes.

## Ownership and behavior

- Root bootstrap reads and validates the library. A compatible existing root completes without an upsert or write receipt. Only a missing root enters the existing issue → local persistence → separate remote acceptance path. The application selects the existing or newly-created readiness state from the bootstrap result. Existing data does not manufacture a “Saved”/“Synced” claim; the account panel simply omits that operation-status message. Recovery, account replacement and shutdown still use DLF's existing owners.
- Search starts dormant, retaining only collection headers. Opening the search popover or submitting a nonempty query admits its resource actor, snapshot subscription and text load. The worker still owns fingerprinting, cache restore/build and queries. Collection/snapshot invalidations are coalesced for one frame. An invalidation during a native load marks that load stale; the chart drains it, discards its result, then loads the latest rows. Jazz's public `all` API has no AbortSignal. The adapter checks cancellation before reads and before constructing search documents; it does not claim to cancel an issued native query.
- The collection explicitly tracks the first result of the article, document, organization and tag subscriptions in parallel states. It publishes only after all initial results arrive and coalesces subsequent same-turn updates before projection. Absent optional subscriptions contribute an empty result. Failure/shutdown disposes all subscriptions and cancels pending publication. The tag dialog waits for the selected tags to reach the rendered row before restoring focus, so a delayed collection update cannot remove a just-refocused chip.
- After validating the document header, the reader invokes snapshot, asset and source reads in parallel. Required snapshot validation still rejects missing/corrupt content. Optional asset/source failures preserve text fallback. The parent waits for the three regions, owns cancellation and discards results from an expired account scope.
- Shell, reader and capture controls use narrow selectors. Reader projections are cached by immutable actor snapshot; filtered library rows/readability are cached by the row array and their actual filter/search/progress inputs. Account eligibility is checked before cache reuse. The library initially renders 50 articles; the existing `Show articles` action appends another 50, moving keyboard focus to the first newly rendered article. Query/filter changes reset the batch. Search and filters still operate on the entire collection; readers remain addressable by URL regardless of their list batch. This bounds initial rendering, rather than virtualizing the entire scrolling list.

Service worker installation, runtime asset caching and the one-WASM-download admission policy are unchanged. Capture workers retain their existing automatic resume, coordination and shutdown behavior. Index validation still reads/hashes the full searchable text once search is activated; incremental revision-based index validation is a separate future optimization.

## Production comparison

Local headless Chromium on macOS, Node 25.2.1, identical public app/server configuration and production builds with debug disabled. A temporary additional entry exported the test-only domain-save fixture in both builds; it is absent from ordinary builds. Profiles were copied only after closing the seed browser, so each build started with the same disposable identity and saved local records. The populated fixture contains 120 articles and roughly 1.3 MB of snapshot text (plus their saved assets). The HTTP cache was cleared before each navigation; service worker caching remained enabled.

The table reports medians for repeat launches after initial service worker installation: two normal-CPU samples and three 4× CPU-throttled samples per build/dataset. Throttling is a controlled comparison, not a claim to represent a particular device. The populated-list milestone is the first rendered batch: all 120 articles in the baseline, 50 in the candidate. No performance threshold is baked into tests.

| Dataset / CPU | Baseline usable controls | Improved usable controls | Baseline first list | Improved first list |
| --- | ---: | ---: | ---: | ---: |
| Empty / normal | 167 ms | 161 ms | — | — |
| Empty / 4× | 541 ms | 492 ms | — | — |
| 120 articles / normal | 179 ms | 172 ms | 507 ms | 422 ms |
| 120 articles / 4× | 549 ms | 476 ms | 1,440 ms | 994 ms |

For the populated 4× comparison, median main-thread long-task time before the first list fell from 896 ms to 489 ms. Normal-CPU long tasks before the first list fell from about 132 ms to zero in these two samples. Single normal-CPU direct-reader observations were 576 ms (baseline) and 479 ms (improved); these are individual samples, not medians. Repeat page WASM requests transferred zero network bytes in both builds. The baseline started search and capture workers on every launch; the candidate started only the capture worker until search was requested.

## Regression coverage

Unit checks cover the existing-root no-write path and honest readiness reporting, shutdown while creating a missing root, concurrent reader reads and account-scope rejection, dormant search admission, draining/coalescing stale loads, and projection reuse without crossing an expired account binding.

The populated browser case saves through the actual domain owner, restarts, verifies the first 50 rows, reaches all 120 via batching, checks keyboard focus after expansion, finds body text in the oldest article outside the initial batch, resets batching through query/filter changes, and opens that reader directly without starting search. Existing suites qualify account recovery, cross-client search refresh, tag keyboard behavior, capture resumption, reader restoration and production offline startup/update/failure handling.

Local validation: `pnpm verify` passes 650 tests (one platform skip), formatting, lint, strict web/service-worker/extension types and production build. All five production offline cases pass, including a cold reader restart with web/Jazz stopped and HTTP cache cleared, one initial WASM transfer, updates waiting for old tabs, failed update cleanup and first-install failure → retry without identity replacement. The complete web run passed 60 of 62 cases. Its image-format helper still expected a new root receipt after reopening an existing library; that assertion was corrected and the case passed. The remaining Firefox live-upgrade case hit a 90-second timeout plus worker-teardown timeout, then passed unchanged in an isolated traced run (26.1 s); the same isolated baseline case passed in 27.4 s. Thus all 62 web cases are qualified, but the original full run was not green. All 11 packaged-extension cases pass in one final run, and both sample-data startup cases pass. The extension recovery fixture now disposes its owned tab directly rather than racing a transient dialog teardown. Local browser ports were redirected to 5280/5281 (5282/5283 for samples) to preserve existing servers; fixture ports were restored afterward.
